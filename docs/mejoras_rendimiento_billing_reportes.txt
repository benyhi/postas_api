Current behavior:
Cada validacion de billing creaba una conexion HTTP nueva. Los reportes cargaban
ventas completas para agrupar pagos en Python y los filtros de fechas usaban
transformaciones DATE sobre created_at. El reporte por metodo de pago sin fechas
no aplicaba el default documentado de hoy.

Proposed behavior:
Los entitlements booleanos de reportes usan una cache corta y segura por tenant
y feature. El cliente HTTP reutiliza una Session con pool. Los reportes agregan
pagos simples en SQL, leen solo el JSON de pagos mixtos y filtran fechas mediante
rangos datetime sargables. Las consultas frecuentes de ventas tienen indices
compuestos y precargan relaciones usadas por los serializers.

Implementation plan:
1. Configurar cache local/Redis y limitarla a basic_reports/advanced_reports.
2. Reemplazar urllib por requests.Session reutilizable sin retries automaticos.
3. Optimizar agregaciones, rangos de fechas y select_related.
4. Agregar indices compuestos mediante migracion sin backfill.
5. Verificar tests, configuracion Django/Docker y planes PostgreSQL disponibles.

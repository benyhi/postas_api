Current behavior:
postas_api already had a PlatformBillingClient and document_extractor checked document_extraction before IA work. Other product, cashbox, supplier, user, sale and report flows did not enforce platform plan limits or usage. Platform collapsed inactive subscription statuses into subscription_inactive and did not deny expired current_period_end with a specific code.

Proposed behavior:
postas_platform_api remains the source of truth for plan catalog, subscriptions and usage. postas_api performs explicit endpoint-level guards through apps.platform_billing.enforcement. The policy is fail closed: protected writes/reports do not proceed when platform denies or when platform is unavailable.

Implementation plan:
1. Classify platform subscription denial reasons in BillingService._check_entitlement using existing TenantSubscription fields.
2. Add reusable postas_api helpers for entitlement checks, check-and-consume, stable error payloads and status-code mapping.
3. Apply guards only in protected endpoints/flows, not as global middleware.
4. Keep sales usage inside the transaction so billing failure rolls back sale, details and stock.
5. Preview product imports before writing to calculate projected new products.
6. Update focused tests, README and OpenAPI schema.

- GET /api/v1/billing/current-plan/: read-only snapshot. Platform returns effective subscription status; expired periods surface as subscription_expired and features are disabled for effective access.

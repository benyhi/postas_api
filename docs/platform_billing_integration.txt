Current behavior:
postas_api called postas_ai_api directly for document extraction and used local settings for document extraction limits.

Proposed behavior:
postas_api treats postas_platform_api as the source of truth for plan entitlements and usage. Document extraction checks feature_key=document_extraction before IA work and performs an atomic check-and-consume after a usable final IA response.

Implementation plan:
1. Add an internal platform billing client with required service headers and controlled errors.
2. Add platform settings and env examples.
3. Integrate document extraction entitlement check before upload/IA work.
4. Register document extraction usage with deterministic idempotency key after successful usable results using check-and-consume to avoid quota races.
5. Add focused client and document extraction tests.
6. Update README documentation.

Risks:
- Exact platform response fields beyond allowed/detail/message are inferred from the requested contract.
- Usage idempotency is server-owned; postas_api sends deterministic keys and accepts duplicate 409 responses only when explicitly marked as duplicate/idempotent.

Important notes:
- No billing tables or local plan catalog were added to postas_api.
- postas_front and MercadoPago were not modified.
- Document extraction intentionally uses entitlement check before IA and check-and-consume after the usable IA result so concurrent extractions cannot overrun the platform quota.
- usage/consume responses must explicitly confirm consumption, return a usage id/object, or indicate duplicate/idempotent replay; otherwise postas_api fails closed.
- Explicit negative usage fields such as allowed=false or consumed=false are never treated as success, even if the response includes an id.
